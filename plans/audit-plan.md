# План разработки AAAA_game

> Unity 6000.2.8f1, мобильная платформа (Android/iOS), Input System.
> Обновлено 2026-10-01 с учётом концепции игры. Этапы 1–5 выполнены 2026-10-01 (замер на устройстве — открыт).
> Этап 6 (ядро скиллов + тестовый персонаж) и доработка баланса этапов 3–4 — 2026-10-01.
> Тесты: 108 EditMode + 14 PlayMode, все зелёные.

---

## 0. Концепция и зафиксированные решения

**Игра:** PvP-файтинг 1 на 1 с элементами MOBA. Единственный смысл — бой с другим игроком. От MOBA — камера,
разные персонажи с уникальными скиллами, мана. Прокачки, предметов, уровней внутри матча **нет**.
Ориентир по ощущениям — Mobile Legends (MLBB), но «больше файтинга, меньше мобы».
Сложность — в управлении: микро-игра жестами.

**Главный приоритет — отзывчивость управления. Ей можно жертвовать чем угодно другим.**

| Тема | Решение |
|------|---------|
| Сеть | Пока локальная сеть (LAN). Архитектура — rollback-неткод, поэтому симуляция боя детерминированная |
| Физика боя | Встроенная физика Unity (Rigidbody/PhysX) в геймплее **не используется** — своё движение и коллизии |
| Ложное срабатывание vs задержка | **Ложное срабатывание лучше задержки.** Действие стартует сразу, распознавание уточняет/отменяет его |
| Общие действия | Удар, парирование, уклонение — у всех персонажей, одинаковыми жестами |
| Скиллы | Уникальные жесты у каждого персонажа; бывают направленные, по области, требующие точности |
| Наведение | Глобального lock-on нет. Цель захватывают только удары и некоторые скиллы; рывки — по направлению свайпа |
| Камера | Как в MLBB: закреплена на своём персонаже, фиксированный угол, не вращается |
| Арена | Рельеф почти не мешает; стены и объекты дают возможность переиграть соперника |
| Ресурсы | HP, мана (только скиллы) и стамина (уклонение, тяжёлый удар) — решено 2026-10-01 |
| Числа в симуляции | Fixed-point Q47.16 — решено 2026-10-01 |
| Тик симуляции | 60 Гц, frame data в кадрах 60 Гц; 120 Гц — смена одной константы `SimTime.TickRate` |
| Формат матча | До 2 побед, раунд 60 с; по таймеру побеждает больший % HP, равенство — ничья; не больше 5 раундов |
| Персонажи | Ближний бой, дальний, маги, гибриды |
| Устройства | Любые; 120 Гц-устройства **допустимо** получают преимущество |

**Рекомендация по вопросу 11 (frame data или анимации):** геймплей задаётся **frame data** (кадры startup /
active / recovery, хитбоксы по кадрам), анимации только подстраиваются под данные (скорость клипа растягивается
под длительность фазы, root motion выключен). Почему:
- скилл-зависимость в файтинге строится на точных, неизменных и выучиваемых таймингах — frame data даёт их
  детерминированно и одинаково на всех устройствах;
- детерминированная симуляция для rollback не может зависеть от аниматора Unity;
- баланс правится числами без переделки анимаций.

## 1. Сделано: первичная доработка (этап 0) — ✅

Проект компилируется без ошибок, 16/16 тестов (9 EditMode + 7 PlayMode), сцена `Arena` без ошибок в консоли.

- Сцена: один игрок из префаба, корректный `Dummy`, один пол. Префабы `Player`/`Dummy`, без reflection.
- EventBus с владельцем подписки, FSM с гарантированным `OnExit` (`Change`/`Stop`), нет утечек подписок.
- Бой: стоимость стамины, hitstun/blockstun от Hitbox, knockback в м/с, слой `Hurtbox`.
- Ввод: мультитач (жест не ломается пальцем на джойстике), блок удержанием работает на устройстве.
- Уклонение относительно камеры, i-frames во времени, кодировки UTF-8 BOM, `com.unity.test-framework`.

> Боевая логика на Rigidbody и `Update`/`FixedUpdate` была **прототипом**; на этапе 3 её заменила
> детерминированная симуляция. Файлы прототипа ещё лежат в проекте (не используются) — см. «Технический бэклог», п. 0.

## 2. Этап 1 — замер задержки и быстрые победы — ✅ (кроме замера на устройстве)

**Цель:** знать задержку в цифрах и убрать очевидные лишние кадры. Без замера отзывчивость нельзя улучшать.

Сделано:
1. **Инструмент замера.** Команда несёт время касания (`Touch.startTime`) и время события, на котором жест
   распознан. `Latency.Log` (`Core/LatencyLog.cs`) пишет каждую команду локального бойца. `LatencyOverlay`
   (кнопка «LAT» слева вверху) показывает последние 8 действий: «всего / жест / игра (кадры) / итог», медианы
   по типам команд, распознанный жест, состояние FSM, FPS, частоту экрана, `targetFrameRate`, vSync. Каждый замер
   дублируется в консоль/logcat строкой `[Latency]`. Время отрисовки берётся по `WaitForEndOfFrame`.
   Вывод на дисплей (композитор ОС, свопчейн, развёртка) сюда не входит — это нижняя граница.
2. **Ввод:** `ProcessEventsInDynamicUpdate` закреплён в коде. `TouchInputProvider` идёт с порядком −2000
   (таймер удержания и эмуляция мышью — раньше бойцов), EventSystem/джойстик — с −1000, бойцы — с 0.
   Длительности жестов считаются по меткам событий Input System, а не по времени кадра (шкалы совпадают с
   `realtimeSinceStartup`, проверено: расхождение 4 мкс).
3. **Кадры:** `targetFrameRate` = максимальная частота экрана среди режимов (Android держит 60 Гц, пока не
   попросишь больше). В `BuildScript` есть варианты сборки для сравнения: Optimized Frame Pacing вкл/выкл и
   2/3 буфера свопчейна Vulkan (меню «Android APK (замер задержки…)» или CLI
   `-framePacing off -swapchainBuffers 2`); имя APK содержит вариант. Для iOS ProMotion в Info.plist
   ставится `CADisableMinimumFrameDurationOnPhone`.
4. **Визуальная задержка:** физика больше не шагает в `FixedUpdate`, который в цикле Unity идёт **до** ввода, и
   интерполяция Rigidbody выключена. `PhysicsStepper` шагает её раз в кадр после Update бойцов: ввод → состояние →
   физика → рендер в одном кадре. Шаг пока переменный (`Time.deltaTime`, ≤ 50 мс); это мост до фиксированного
   тика этапа 3.
5. **Тесты:** `LatencyLogTests`; PlayMode-тест «рывок сдвигает бойца в первом же кадре».

**Базовые цифры («до», задавались устройством старого распознавателя):** тап ждал отпускания пальца
(задержка = время контакта, обычно 60–120 мс, до 180 мс); блок — 180 мс удержания; уклонение и парирование ждали
отпускания (длительность свайпа, до 300 мс); рывок становился виден через ≥ 1 кадр из-за `FixedUpdate` (50 Гц)
плюс 1 шаг интерполяции.

**Замер в редакторе (144 Гц, виртуальный тачскрин, после этапа 2):** задержка игры от события ввода до конца
рендера — 1,5–6 мс, то есть 0,2–0,8 кадра для всех команд; команда и рендер в одном кадре.

**Осталось на устройстве:** собрать 2 APK (`fp-on_sc3` и `fp-off_sc2`), сравнить медианы оверлея, выбрать
вариант по умолчанию. От этого зависит и вопрос 2 (60 или 120 Гц).

**Критерий:** оверлей показывает задержку ✅; известна базовая цифра ✅ (устройство — см. выше);
задержка, добавляемая игрой, ≤ 2 кадров ✅ (в редакторе < 1 кадра).

## 3. Этап 2 — распознаватель жестов «сначала действие, потом уточнение» — ✅

**Сделано** (`Input/GestureRecognizer.cs` — чистый C#, `Input/GestureSettings.cs` +
`Resources/Input/GestureSettings.asset`, `Characters/InputBuffer.cs`, отмены в `States.cs`):

| Жест | Команда и момент | Что делает боец |
|------|------------------|-----------------|
| Касание правой зоны | LightAttack **в момент касания** | удар; startup (6 кадров) — окно распознавания |
| Сдвиг ≥ 6 мм | Dodge **в момент пересечения порога**, направление уже мировое | отмена удара из startup/recovery, бесплатно |
| Flick (≤ 120 мс, ≥ 100 мм/с) | Parry при отпускании | отмена удара из startup/recovery или уклонения (≤ 150 мс, стамина возвращается) |
| Удержание ≥ 90 мс без сдвига | BlockStart; отпускание → BlockEnd | отмена удара из startup в блок |
| Удержание, потом сдвиг | Dodge из блока | |
| **Второй палец**, пока первый на экране | HeavyAttack (решение по вопросу 6) | отмена лёгкого удара из startup в тяжёлый; первый палец больше жестов не даёт |

- Стамина за удар списывается при выходе хитбокса, поэтому отмена в startup бесплатна.
- **Буфер ввода** 120 мс (`Fighter.InputBufferSeconds`): отклонённая команда выполняется в первый кадр, когда это
  разрешено (сразу после Tick, без пустого кадра Idle). Новая команда вытесняет старую; отпускание блока снимает
  буферный блок.
- Пороги — в `GestureSettings`, расстояния в **мм** (Screen.dpi), а не в пикселях.
- Направление свайпа переводится в мир на стороне ввода (`ScreenToWorld`); `DodgeState` камеру не читает.
- Временный вид `FighterStateView` красит бойца по состоянию (startup — жёлтый, active — красный, блок — синий,
  уклонение — зелёный, парирование — белый, hitstun — фиолетовый). Пока нет анимаций, это видимый отклик в кадре
  касания.
- В редакторе: ЛКМ — основной палец, ПКМ — второй палец.
- Тесты: 12 сценариев на записанных касаниях (`GestureRecognizerTests`), `InputBufferTests`, 8 PlayMode-тестов
  на отмены, буфер и видимость удара в кадре команды.

**Известные компромиссы (подобрать на устройстве):**
- Порог удержания (90 мс) должен быть меньше startup лёгкого удара (100 мс), иначе блок не успеет отменить удар.
  Цена — тап дольше 90 мс становится коротким блоком. Если ложных блоков много, увеличить startup лёгкого удара
  или порог.
- Flick = уклонение, которое через ~80 мс отменяется в парирование: персонаж успевает сместиться на 0,3–0,6 м.
- Шаг логики пока переменный: если кадр длиннее startup (подвисание), удар проходит startup за один кадр, и отмена
  не успевает. Исправит фиксированный тик этапа 3.

**Проблемы старого распознавателя (решены):**
- тап распознаётся при **отпускании** пальца (до 180 мс задержки);
- блок включается через 180 мс удержания;
- двойной тап = лёгкая атака + тяжёлая (первый тап уже запустил атаку);
- нет буфера ввода: команда за пару кадров до конца атаки/оглушения теряется.

**Новая модель (следует решению «ложное срабатывание лучше задержки»):**
1. **Касание в правой зоне → удар стартует сразу** (с захватом цели, см. этап 4). Startup-кадры удара
   одновременно служат окном распознавания.
2. Палец сдвинулся дальше порога **во время startup** → удар отменяется в **уклонение** в сторону свайпа
   (отмена бесплатная, без штрафа).
3. Очень быстрый короткий flick → **парирование** (отмена удара/уклонения в парирование).
4. Удержание без движения → **блок** (порог подбирается по замеру; блок может стартовать из startup удара).
5. Тяжёлая атака — отдельный жест, не двойной тап → выбран тап вторым пальцем.
6. **Буфер ввода** ~100–150 мс (настраиваемо): команда, пришедшая во время recovery/hitstun, выполняется в первый
   кадр, когда это разрешено.
7. **Пороги в ScriptableObject** (`GestureSettings`) — тюнинг без перекомпиляции; позже — в настройках игрока.
8. Направление свайпа переводится из экрана в мир **на стороне ввода** (камера не вращается, поэтому это
   фиксированное преобразование) — в симуляцию уходит уже мировое направление.
9. **Тесты на записанных касаниях:** синтетические последовательности (координаты + время) → ожидаемые команды.
   Распознаватель — чистый C#-класс без MonoBehaviour, чтобы тестировать без сцены.

**Критерий:** удар виден в кадре касания + ≤ 1 кадр; ни одна команда не теряется при нажатии чуть раньше окна;
все жесты покрыты тестами.

## 4. Этап 3 — детерминированная симуляция боя (ядро) — ✅

**Цель:** бой — чистая функция `состояние(t) + вводы(t) → состояние(t+1)`. Нужна для rollback, честного LAN и
повторяемых тестов.

**Сделано** — сборка `Game.Simulation` (`Scripts/Simulation/`, `noEngineReferences`: движок недоступен даже случайно):

| Файл | Что внутри |
|------|-----------|
| `Fix.cs` | `Fix` — fixed-point Q47.16 на `long` (шаг ≈ 0,000015), `FixVec2`. Корень — целочисленный, тригонометрии нет: направления хранятся векторами. `FromFloat` — только для данных (ассеты), не внутри тика |
| `SimTypes.cs` | `SimTime` (тик 60 Гц, перевод кадров 60 Гц/секунд/скоростей в тики), `TickInput` (джойстик + до 4 команд за тик, направления квантованы в `sbyte` — готово для сети), `SimEvent` |
| `Specs.cs` | неизменяемые данные: `AttackSpec`, `FighterSpec`, `MatchRules`, `ArenaSpec` (стены + препятствия-круги/прямоугольники) |
| `GameState.cs` | состояние только из значений (`FighterSim` — структура): снимок = `CopyFrom`, `ComputeHash` — FNV-1a 64 |
| `FightSimulation.cs` | `Step(state, input0, input1)`: состояния бойца, отмены, буфер, хитбоксы, раунды |
| `Collision.cs` | выталкивание кругов из стен/препятствий, расталкивание бойцов, `SegmentBlocked` (линия видимости для снарядов этапа 6) |
| `StateHistory.cs` | кольцо снимков по тикам (rollback) и `InputRecording` (запись матча → повтор) |
| `TrainingBot.cs` | бот — чистая функция состояния и номера тика |

- **Порядок тика** (для бойца 0, потом 1): ресурсы → стоп-кадр (только буфер) → таймеры состояния → буферная
  команда → новые команды → бег/стойка → движение. Затем тела, хитбоксы обоих **одновременно** (размен возможен),
  фаза матча. Команда, пришедшая в тик, действует в нём же.
- **Unity-слой** (`Game.Characters`): `MatchRunner` ведёт тик через аккумулятор времени, собирает ввод из EventBus,
  даёт ввод боту, хранит 120 снимков, пишет замер задержки по событиям `CommandAccepted/Dropped`.
  **Досрочный тик:** если в кадре пришла команда, а тик ещё не настал, он выполняется сразу (симуляция обгоняет
  время не больше чем на 1 тик, дальше время её догоняет) — при 144 Гц экрана и 60 Гц тика команда всё равно видна
  в кадре касания. `FighterView` только читает состояние (позиция без интерполяции, цвет по фазе, диск хитбокса
  в active-кадрах). Данные бойца — `FighterDefinition` (`Resources/Fighters/Fighter_Default.asset`) + `AttackData`,
  `ToSpec()` переводит их в fixed-point и тики.
- В сцене нет Rigidbody: коллайдеры примитивов удаляются, `PhysicsStepper` больше не ставится.
- **Тесты:** sync-тест (две копии, 5000 тиков, случайный ввод + боты с обеих сторон, хеш каждый тик), откат на 12
  тиков с пересчётом каждые 37 тиков, повтор записи → тот же хеш, независимость снимка; плюс тесты Fix и коллизий.

**Критерий:** бой проигрывается из записи вводов одинаково ✅; sync-тест зелёный ✅; в геймплее нет Rigidbody ✅.

## 5. Этап 4 — боевая модель — ✅

1. **Захват цели ударом** ✅: удар поворачивает к противнику ближе `MatchRules.LockOnRadius` (4 м), иначе — вперёд.
   Поворот при беге мгновенный (отзывчивость важнее плавности).
2. **Frame advantage** ✅: событие контакта несёт преимущество по тикам; оверлей показывает «у вас +3 тиков» после
   каждого контакта. Тест сверяет число с тем, кто на самом деле начал действовать первым. Подобраны значения:

   | Удар | Startup / Active / Recovery | Hitstun / Blockstun | На попадании | В блоке | Стоп-кадр |
   |------|-----------------------------|---------------------|--------------|---------|-----------|
   | Лёгкий | 6 / 3 / 12 | 18 / 10 | **+3** | **−5** | 3 |
   | Тяжёлый (25 стамины) | 14 / 4 / 28 | 34 / 18 | **+2** | **−14** (наказуем) | 6 |
   | Парирование | — | атакующий оглушён 30 | **+30** у защитника | — | 8 |

3. **Награда за парирование** ✅: атакующий — `ParryStunned` на 30 кадров, защитник сразу свободен (гарантированная
   контратака лёгким ударом, тест есть), стоп-кадр 8. Парирование мимо — 8 кадров уязвимости (`ParryRecovery`),
   иначе его можно спамить бесплатно.
4. **Отмены** ✅: startup → уклонение/парирование/блок/тяжёлый; recovery → парирование/уклонение; после попадания
   или блока active/recovery → следующий удар (`CanCancelOnHit`, у лёгкого вкл., у тяжёлого выкл.) — лёгкий в лёгкий
   — настоящее комбо. Ввод в стоп-кадре уходит в буфер и срабатывает сразу после него.
   Блок «держится»: если палец на блоке, а удар/оглушение не дали встать в блок, боец встаёт в него сам.
5. **Смерть и матч** ✅: `Dead`, раунды (до 2 побед, 60 с, отсчёт 1,5 с, пауза после KO 2 с), победа по % HP по
   таймеру, ничья, предел 5 раундов, рестарт **командой через симуляцию** (в сети будет синхронным).
   HUD матча: таймер, счёт, «Раунд N» / «Бой!» / «KO» / «Время!» / «Победа», кнопка «Ещё раз».
6. **Мана** ✅ (ресурс и регенерация, полоска в HUD; тратить будут скиллы этапа 6). Стамина — уклонение и тяжёлый удар.
